AHAM · 实践笔记

 

2026.08

App 不会消失，但会从交互中心退到能力载体。

 

过去做软件，我们先画页面、菜单和流程。用户要完成一项工作，得先判断打开哪个 App，再学习字段藏在哪里。软件组织工作，人去适应软件。

Agent First 把这个顺序倒了过来。人先说目标，Agent 决定要读什么、查什么、调用什么。App 仍然存在，只是不再垄断入口。

图 1 · 从 UI First 到 Agent First

 

01  ·  入口

用户真正掌握的是目标

“准备明天的客户调研”不是某个按钮。它可能同时需要阅读客户资料、搜索行业工艺、整理问题、检查历史记录，再把结果放进一个调研工具。

传统 App 会把这件事拆进多个页面。Agent 可以先理解目标，再临时组织路径。工作的入口从菜单变成了自然语言。

 

02  ·  单元

软件正在从 App 变成能力

过去的软件交付单元是一个完整 App：界面、流程和能力绑在一起。新的交付单元，可能是一组能被 Agent 理解、调用和组合的能力。

这时，App 更像一个有状态的领域节点。它保存事实，执行确定规则，处理权限和审计，也保留适合人操作的专业界面。

图 2 · Agent First 的四层结构（全文唯一深色重点图）

Agent

 

理解目标，调动模型、搜索、文件和多个软件。

Skill

 

把业务方法、步骤、边界和恢复方式写成可复用说明。

MCP

 

向 Agent 暴露可发现的工具、资源和 Prompt。

App

 

拥有真实状态，校验动作，并把结果留在可继续工作的地方。

 

03  ·  开发

起点不再只是页面

这会改变产品设计的第一轮问题。页面仍要做，但在画页面之前，要先划清软件和 Agent 的责任。

图 3 · Agent First 带来的开发问题变化

最关键的一刀，是区分确定性与不确定性。数据结构、合法状态和写入规则交给代码；需要研究、理解和动态判断的部分，交给 Agent。

变化最快的部分，也不必每次跟着 App 发布。行业方法改变，可以更新 Skill；模型能力改变，可以更换 Agent；数据结构和校验规则仍由 App 保持稳定。

 

04  ·  智能

最难的功能不必写死在 App 里

以制造业调研为例，一套标准题库只能守住最低覆盖线。真正难的是理解客户产品、行业工艺和现场异常，再决定下一步问什么。

如果把这些都塞进 App，开发者还得自己维护模型接入、网络搜索、文件解析和长流程调度。Agent 平台原本就拥有其中不少能力。

新的做法是让 Agent 完成研究和推理，让 Skill 规定方法，再通过 MCP 读取 App 的真实状态，把确认后的结果交还给 App。

图 4 · Agent、Skill、MCP 与 App 的运行循环

 

MCP 不是 API 的替代品。底层仍可能是 API、数据库或本地服务；MCP 补的是面向 Agent 的发现和调用方式，Skill 再补上“何时用、按什么顺序用”。资料来源：MCP Architecture Overview（modelcontextprotocol.io/docs/learn/architecture）和 Agent Skills 开放规范（agentskills.io/home）。

 

05  ·  实验

我先在一个 App 里试了试

我用 Aham Survey 做了一次小实验：专业界面继续承担现场记录和人工复核；项目创建、题目读取、答案预览与提交、报告导出，则可以由 Agent 按 Skill 通过 MCP 完成。

图 5 · Aham Survey 真实界面，只作为范式落地证据

这段实践的意义不在调研工具本身。它让我看到：一个 App 可以同时面向人和 Agent，而不必把全部智能绑定在自己的进程里。

 

06  ·  边界

这还不是所有软件的答案

实时控制、复杂编辑、视觉分析和高风险确认，仍需要专门界面。Agent 也会带来权限、成本、延迟、错误恢复和平台差异。

 

我不确定 Agent First 会不会成为所有 App 的默认形态。能确认的是：面对跨资料、跨工具、需要研究与判断的复杂任务，传统的“先打开 App 再找功能”已经不是唯一入口。

接下来真正值得讨论的，是哪些规则必须留在代码里，哪些方法可以交给 Skill，哪些能力适合经 MCP 开放，以及人应该在哪一步确认。

 

App 不会消失，
但会从交互中心退到能力载体。
